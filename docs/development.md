# Development

This page is for working on the pack itself: setting up, the checks, the local site and releases. To use the pack in a theme, read [use-in-your-theme.md](use-in-your-theme.md). The rules every change keeps are in [AGENTS.md](../AGENTS.md) and [CONTRIBUTING.md](../CONTRIBUTING.md). Starter tasks are in [good-first-issues.md](good-first-issues.md).

## Quick start

`npm run dev` boots WordPress Playground with your checkout mounted, the plugin active, demo Site Data and the demo pages. Start here when you want to see a change in a browser.

```bash
git clone https://github.com/voyager-marketing/voyager-open-blocks.git
cd voyager-open-blocks
npm ci
npm run dev
```

## Set up

You need Node `^22.23.4 || ^24.22.1 || >=26.12.1`, Block Runner 1.0.0's range. `.nvmrc` pins 24.22.1. The local site below also needs PHP 8.1+ and WP-CLI on `PATH`.

```bash
npm install
npm run build              # blocks
npm run patterns:build     # intents -> patterns/*.html
npm run check              # every offline gate, below
```

## How it is built

- **Blocks** live in `src/<name>/` and build with `@wordpress/scripts` (`npm run build`, which writes `build/blocks-manifest.php`). The plugin registers everything in that manifest. `build/` is committed so a Git install works without a build step. CI fails when `build/` is stale.
- **Patterns** start as Block Runner intent trees in `patterns/intents/<name>.json`, with the pattern's title, description and categories beside the tree. `npm run patterns:build` assembles each one into `patterns/<name>.html` and fails on any invalid block, any dropped attribute, and two blocks in one pattern with the same `metadata.name`. The pack's own blocks, such as the icon, can sit in an intent too. Block Runner cannot assemble a block it does not know, so a core block stands in for each one while it assembles and the pack block's comment goes back in its place, its attributes checked against its `block.json` (an icon name outside the set fails the build). A pattern that holds one is validated again with the pack's blocks in place (`scripts/lib/pack-blocks.mjs`). Do not edit the `.html` files by hand.
- **Binding sources** are in `inc/site-data.php` and `inc/post-meta-text.php`. Their editor half (field lists, live values, in-place editing of post meta) is `assets/bindings-editor.js`.
- **Abilities** are in `inc/abilities/`, one file per ability (`get-catalog.php`, `find-posts.php`, `get-post-blocks.php`, `insert.php`, `configure.php`, `bind.php`, `validate.php`), each holding its registration and its callbacks. `shared.php` holds what several use: the permission callbacks, the input schemas, `check_attributes()`, `validation()`, `locate()` and `finish()`, and `register()`, which registers the abilities in order. `inc/abilities.php` only loads them. They are a thin layer over `inc/block-tree.php` (read and write a post's blocks by path) and `inc/catalog.php` (what the pack offers, and which binding args are real).
- **Change notes** for `readme.txt`'s changelog are files in `unreleased/`, one per pull request, folded in by the release pull request. The format is in [unreleased/README.md](../unreleased/README.md).
- **The usage index** (`inc/freshness/usage.php`) records which posts and templates show each Site Data and bindable post meta field, as post meta `_voyager_open_blocks_uses`, written on save. `get-catalog`'s `used_on` and the "Shown on" line under each field on Settings > Site Data read it, and the purge (`inc/freshness/purge.php`) uses it to find the pages a change must refresh. Activation starts a WP-Cron backfill of every post, and `wp voyager-open-blocks reindex` rebuilds it at once. The shapes are contracts 1 and 2 in [v2-contracts.md](v2-contracts.md).
- **DESIGN.md** at the repo root describes the patterns' design in [Google's DESIGN.md format](https://github.com/google-labs-code/design.md). The entry skill tells agents to read it after the site's own DESIGN.md.
- **Skills** are in `skills/`, one per item, beside the entry skill, a quick card kept under 500 words (gate 23). What an agent needs to call an ability goes in that ability's description or its input properties' descriptions, which an MCP client sends as the tool definition, and the card, those descriptions and nothing else stay under 3,000 words (`npm run e2e`). WordPress lists an input schema through `wp_prepare_json_schema_for_client()`, which keeps only the draft-04 keywords `rest_get_allowed_schema_keywords()` names (`wp-includes/json-schema.php` and `wp-includes/rest-api.php` in WordPress 7.1.4), so a JSON Schema `examples` entry never reaches a client over REST: put an example in the description. The long guide for people and for agents with a shell is [agents.md](agents.md). It ships in the plugin zip, so the copy in the plugin's folder matches the version installed.
- **The v2 contracts**, the shapes the lanes of version 2 build against, are in [v2-contracts.md](v2-contracts.md). The lanes are in [AGENTS.md](../AGENTS.md#lanes).

## The offline gates

`npm run check` needs no WordPress. It fails unless:

1. every `patterns/*.html` matches its intent,
2. `block-runner validate --strict` passes on all pattern markup, given a Wesper site context that lists the pack's own blocks, `tests/fixtures/pack.context.json`. `npm run patterns:build` writes it from every `block.json` under `build/`, so a block added to `src/` needs no list edited by hand, and this gate fails while the committed file differs from what `build/` gives or `wesper validate` refuses it. No block may warn `unregistered-block`. The same run without the context must warn `unregistered-block` on the pack's blocks and report everything else the same, so the context is shown to pass the pack's blocks and change nothing else,
3. the same validator rejects `tests/invalid/`, so the gate is shown to bite, and `tests/invalid/blocks/`, which holds an icon and a block no plugin registers, so the context is shown to know the pack's blocks and no others,
4. `block-runner plugin inspect` recognizes the plugin as a `@wordpress/scripts` host. On Windows this step is skipped: Block Runner 1.0.0 compares `__DIR__ . '/build'` with a native path and never matches a backslash path.
5. `Stable tag` in `readme.txt` matches `Version` in `voyager-open-blocks.php`.
6. the entry skill's `pack-version` (`skills/voyager-open-blocks/SKILL.md`) matches `Version` in `voyager-open-blocks.php`.
7. `tests/fixtures/site-data-keys.json` matches the hash in `tests/fixtures/site-data-keys.sha256`.
8. `readme.txt` has a `= Source code =` section with the GitHub link and `npm run build`. The plugin directory asks a plugin that ships built files to say where their source is, and Plugin Check does not test for it.
9. `readme.txt`'s `== Changelog ==` has an entry, `= <version> =`, for `Version` in `voyager-open-blocks.php`. A release pull request bumps `Version`, so it stays red until `npm run changelog:fold` writes its notes in.
10. every change note in `unreleased/` is well-formed (`npm run changelog:fold -- --check`),
11. `scripts/fold-unreleased.mjs` passes its known-answer test, `scripts/test-fold-unreleased.mjs` (`npm run test:fold`), all 12 of its cases: the notes in `tests/fixtures/fold-unreleased/` folded into its `readme.in.txt` must give `readme.expected.txt`, and malformed notes must stop the fold with nothing changed,
12. `DESIGN.md` lints with `@google/design.md` (`npm run lint:design`) with no errors and no warnings. Contrast under 4.5:1 between a component's colours, an unused colour and a section out of order are all warnings,
13. the same linter rejects `tests/invalid/design-broken-ref.md`, a component pointing at a colour token that does not exist, so that gate is shown to bite,
14. the gate in 12 rejects `tests/invalid/design-low-contrast.md`, which the linter passes with one contrast warning and exit 0, so the rule that fails on any warning is shown to bite,
15. the logic of `npm run cache-check` passes its known-answer test, `scripts/test-cache-check.mjs` (`npm run test:cache-check`), all 32 of its cases, including crashes planted in each step, which must exit 2 and never pass a row,
16. the guard on 11 and 15 rejects `tests/invalid/no-tests.mjs`. `node --test` reports a file with no tests as one passing test, so the guard counts each file's known cases rather than "more than none".
17. no tracked file but `CHANGELOG.md` and `bench/runs/` holds a tracker issue ID. The same `git grep` must find one planted in a temporary file, so a search that cannot match fails too.
18. `presets`: no block in `patterns/*.html` sets a colour, font size, font family, radius or shadow that is not a theme preset, uses a spacing slug outside `20` to `60`, or is `core/html` or HTML outside a block (`scripts/lib/presets.mjs`). It reads the block comments. A value passes as a slug attribute (`textColor`, `fontSize`, `borderColor`) or as a preset reference of the right kind (`var:preset|color|accent`, or `var(--wp--preset--color--accent)`). Each finding names the pattern, the block's path (`0/1/2`, as the abilities write it) and the attribute,
19. the same gate refuses every block in each of the seven files in `tests/invalid/presets/`, one file per rule, for that file's rule and no other,
20. the same gate passes `tests/fixtures/presets/allowed.html`, which writes every preset form it accepts, so a rule grown to refuse a preset fails too.
21. the verdict of `npm run check:usage-index` (`run()` in `scripts/usage-index-check.mjs`) passes its known-answer test, `scripts/test-usage-index-check.mjs`, all 12 of its cases. Crashes are planted before the paths are measured and after they pass, and none may exit 0; the script itself run with `--plant crash` must exit 2.
22. each of `known_failures` in `tests/fixtures/contrast.json` names its pair by where it is, the kind of target and its place among the section's targets of that kind (`"kind": "outline button", "nth": 1`), never by the text it shows, so new Site Data or new wording in a pattern does not rename the list. The same rule must refuse a planted entry keyed on text.
23. `skills`: the quick card, the entry skill, is under 500 words, counted as `wc -w` counts them (`scripts/lib/words.mjs`), and the line prints the count. The same rule must refuse `tests/invalid/quick-card-500.md`, a copy of the card at exactly 500 words. The detail an agent needs lives in each ability's own description, and the long guide is [agents.md](agents.md).

The rest of what CI runs:

```bash
npm run lint:js
npm run lint:css
composer install           # once, for the two PHP checks below
composer phpstan           # PHPStan at level max over the plugin file, inc/ and src/, no baseline
composer test              # PHPUnit unit suite, no WordPress needed
npm run plugin-check       # Plugin Check, activation and uninstall on the zip in a fresh WordPress (needs wordpress.org)
```

`npm run plugin-check` does not run on Windows: under Playground there, PHP_CodeSniffer's reporter writes its cache with an exclusive lock the stream does not support, and the run stops. CI's Plugin Check job, on Linux, is the run that counts.

## Local site

A throwaway WordPress on SQLite that WP-CLI, Playground and Wesper all read from the same files. Use it when you need a site that lasts between runs, or WP-CLI against it. It needs `wp` and `php` on `PATH`.

```bash
npm run playground -- setup --site ../voyager-open-blocks-site   # install WordPress + SQLite, link this checkout, seed demo pages
npm run playground -- serve --site ../voyager-open-blocks-site   # serve it with Playground at http://127.0.0.1:9400
npm run context -- --site ../voyager-open-blocks-site            # wesper collect, then check every item is listed
npm run playground -- blueprint cta-band                         # boot blueprints/cta-band.json with this checkout mounted
```

Two setup details that matter: the SQLite journal mode is set to `DELETE`, because Playground's WebAssembly PHP cannot share WAL's index with host PHP. And the site lives outside the checkout, because the checkout is linked into it.

`npm run context` fails if Wesper's manifest is missing any block, binding source or pattern in this repo, or carries a warning that names one. Other warnings are printed. WordPress 7.1.3 itself produces three (`core/navigation` and `core/query` provide context from attributes they no longer register), with or without this plugin. Run it when registration changes.

### End to end over REST

With a site served, `npm run e2e -- --context site.context.json` runs the abilities end to end over REST, the way an agent with only MCP or REST access would. It first counts what an agent reads before its first call: the quick card, and each ability's description and every description in its input schema as `/wp-abilities/v1/abilities` serves them. It prints each part and fails at 3,000 words or more, and the same rule must refuse the listing with a planted 3,000-word description added. What an ability returns is not counted. Then it finds pages, inserts the CTA band (as shipped, then with copy), places an icon inside the header beside its call button, builds a proof strip with more credentials than the pattern ships, binds post meta in a template, and configures and binds an icon. It checks that bad input and a contributor without permission are refused, runs `block-runner validate --strict` on every markup returned and on the saved pages, checks the bound values render, and deletes what it created.

It reads an application password from `VOYAGER_OPEN_APP_PASSWORD` (`wp user application-password create admin e2e --porcelain`). `setup` sets `WP_ENVIRONMENT_TYPE` to `local` so application passwords work over plain HTTP.

The quickest way to get a site for it needs no `wp` or `php`: `npm run dev -- --no-login --ready-file site.json` boots the dev site in the background and writes its URL and a fresh application password to `site.json`. That is what CI does.

### End to end in the block editor

`npm run e2e:editor` boots its own fresh dev site and drives headless Chrome, logged in as admin. It checks the first-run notice, the "Used by" and "Shown on" lines on Settings > Site Data, the editor's empty-value warning, the placeholder hints (including copies from another host or folder, and a cover and a media and text block over the image slots' placeholders), that each pattern's markup pastes into the editor as valid blocks, and that no editor-only hint reaches the front end. Its check g covers theme files: a template part that is only a file in the active theme, with the phone bound in it, is counted in `get-catalog`'s `used_on` once `switch_theme` rebuilds the theme index, and not before. It needs Chrome or Chromium; set `CHROME_PATH` if it isn't found. `--only a,c` runs some checks; `--help` lists the options.

### Design checks

`npm run design-check` runs the rendered checks in [DESIGN.md](../DESIGN.md#dos-and-donts). It boots its own fresh dev site for each WordPress version the themes in `tests/fixtures/contrast.json` name: Twenty Twenty-Five and Twenty Twenty-Four on 7.1.4, the release that bundles them, and Ipsum, WordPress's proposed default theme, on 7.2 beta 5, since it requires 7.2. Ipsum is not on WordPress.org, so the fixture pins it to a commit and the run installs that commit from GitHub. It has no built-in role map, so it runs on the fallback roles. On each theme the run builds one page that holds every pattern in `patterns/` once per section style: plain, panel, inverted and accent. A new pattern is picked up with no fixture change. It loads the page in headless Chrome at 320, 390, 768 and 1280px and runs six checks on each section:

- `contrast`: every element that holds text, measured against its background from computed styles, at rest, and links and buttons hovered too. The background is composited through translucent ancestors, and a background image on the way counts as a failure. Text in a `core/cover` that shows an image is measured against the cover's overlay (its `span.wp-block-cover__background`, at the opacity its `dimRatio` gives it) composited once over black and once over white, the two extremes any image can reach, and the lower ratio counts. A gradient overlay counts as a failure. The floor is 4.5:1.
- `overflow`: something in the section reaches past the right edge of the viewport with nothing in the section to clip it, or the document is wider than the viewport, so the page scrolls sideways.
- `motion`: with reduced motion emulated, an animation or transition is running in the section, or a box in it moves between two samples 400ms apart. The run also checks it sees the logo marquee loop and the services and reviews rows reveal with motion on, in every style, so a still render with motion off is their reduced-motion rule at work.
- `layout`: with reduced motion emulated, so a revealed row is where it rests, every row of items in the section (a `core/columns`, or a group with the grid layout) renders the columns the fixture's `layout.columns` names for its pattern at 1280px, and one column at 320 and 390px. A row's columns are its children that sit beside the highest one. A pattern the fixture does not list must hold no row. In every heading, a word that breaks across lines, or reaches past its heading's box, fails, so a card too narrow for its heading cannot pass. A word is what sits between a space, a hyphen or dash, a soft hyphen or a slash.
- `a11y`: axe-core 4.14.0, put into the page, runs on the sections only, with every rule tagged `wcag2a`, `wcag2aa`, `wcag21a` or `wcag21aa`, and `heading-order`, which axe tags best practice. The theme's markup around the sections is outside the scan, and page-level rules, such as landmarks and the document title, do not run. `heading-order` still compares a section's first heading with the heading before it on the page. Any violation fails the section.
- `impeccable`: `impeccable detect --json --no-config` (Impeccable 4.8.2) scans the whole page at that width in its own headless Chrome. Each finding is placed in the section its CSS selector matches in the run's own copy of the page. A finding in a section fails it when its rule is one of the four the fixture gates: `line-length`, `gradient-text`, `nested-cards` and `gray-on-color`. Every other finding is an advisory, and so is a gated one in the theme's own markup outside the sections. Impeccable 4.8.2 has no tap-target rule, so the check also measures tap targets itself, as `tap-target`: every link, button and form control in the section must be at least 44px tall and wide, apart from a link inside a sentence, which WCAG exempts.

A few things about Impeccable's rules, read from its source at 4.8.2. `line-length` aims for under 80 characters and charges a paragraph only when two or more of its rendered lines run over 85, which is looser than DESIGN.md's 75. `nested-cards` counts a box as a card only when it is rounded or casts a shadow, so the pack's square cards are invisible to it until a theme rounds them; the planted cards are rounded. `--no-config` keeps an `impeccable-disable` comment in the markup from waiving a finding, and keeps this repo's DESIGN.md out of the scan. A scan that exits 1, or prints anything but a findings array, fails the run: it is a scan that did not happen, never a pass. So does a gated finding whose selector matches nothing in the page, since the run cannot tell whose it is.

Twenty Twenty-Four's own buttons, fill and outline, measure 41.5px tall at every width. The fixture lists them under `impeccable.tap_target.known_gaps` for that theme only. A target of that kind within 0.5px of the listed height passes there, any other target under 44px fails, and a listed gap the run no longer measures fails too, so the list stays true.

Every run has twelve controls, and each must fail its own check: the fixture's low-contrast role map, planted through the `voyager_open_blocks_style_roles` filter; white text on a cover with a white overlay at 50% over the pack's 16:9 placeholder, which must fail `contrast` at the composites worked out from its colours (`#808080` over black, `#ffffff` over white); a section with an element 400px wide, loaded at 320px; a CSS animation with no reduced-motion rule; an h2 followed by an h4, which must fail `a11y` on `heading-order`; and gradient text, a card inside a card and a 30px tall button, each of which must fail `impeccable` on its own rule (`gradient-text`, `nested-cards` and `tap-target`); and four for `layout`, each on its own reason: a grid of three cards at least 60rem wide each, which renders one column at 1280px; three columns not stacked on mobile, at 320px; and the word "Installation" in a heading 4em wide, once free to break anywhere and once not, which must break and spill. One more must pass: white text on a cover with a black overlay at 80%, at 12.63:1. Measured against the page behind the cover instead, it would read white on white, so it shows the check reads the overlay. `--plant` puts every planted section into the main run as well. The run then exits 1 and prints `Planted run: every check failed on its planted faults, and nothing else failed.` only when each check it ran failed on that check's own plants and no other assertion failed; otherwise it says what went wrong and exits 3. A crash exits 1 too, with no such line, so CI's `--plant` row needs both. On Twenty Twenty-Five and Twenty Twenty-Four it also opens the page in the block editor and checks the Styles panel and the canvas.

Then it switches on each colour style variation the three themes ship, the way the Site Editor saves one: the variation's settings and styles go into the theme's global styles post. It measures `contrast` on each at 390 and 1280px; the other four checks run on the theme's own styles only. A pair under the floor fails unless the fixture lists it under `known_failures` with its ratio, and a listed pair that no longer fails fails too, so the list stays true. Every listed pair comes from a variation: Plain-section outline button hovers on Twenty Twenty-Five's Morning and Twenty Twenty-Four's Maelstrom, and the hero cover's text on Twenty Twenty-Five's Afternoon. Each names its target by kind and place in its section, never by its text. On Ipsum, the theme with no built-in role map, the run also saves a text and a background colour in the Site Editor's global styles (`site_editor_colours` in the fixture) and checks every Panel, Inverted and Accent section paints from them, as the fallback roles work them out: Inverted the text with the background as text, Panel 5% of the text in the background, and Accent the text mixed into the background at the first share from 75% that reads at 4.6:1. Then it clears them. The site has background updates switched off, because a beta updates itself and answers 503 while it does.

Each of `overflow`, `motion`, `layout`, `a11y` and `impeccable` prints one row per section render: `ok` or `FAIL`, the check, the theme, the width, the pattern and the style, then what it found. An `a11y` row names the axe rule, its impact, the element and axe's summary, such as `heading-order (moderate) at h4: Fix any of the following: Heading order invalid`. An `impeccable` row names the rule and the selector Impeccable gave, such as `nested-cards at section.wp-block-group.alignfull:nth-of-type(5) > div > div: Card inside card`, or `tap-target` with the height and width measured. A known gap reads `known gap: tap-target ...` and passes. After the rows come the advisories, counted by rule with the first three of each: axe's incomplete results, which need a person to judge, and every Impeccable finding the run does not gate on. Most of those judge the theme, such as `overused-font` on Twenty Twenty-Four's Inter, or are style notes, such as `kicker-above-heading` on the CTA band's eyebrow. They never fail the run.

It prints how many renders and contrast pairs it measured, how many section renders `a11y` and `impeccable` scanned, how many axe rules ran and how many pages Impeccable scanned, exits 1 on any failure, and in CI writes the failures to the job summary ([`e2e.yml`](../.github/workflows/e2e.yml), job `contrast`). `npm run contrast` is the contrast part alone (`--checks contrast`). `--themes`, `--no-variations` and `--checks` make a quicker local run; `--help` lists every option.

### Usage index check

The dev site activates the plugin before it seeds its pages, so every page there is indexed on save, and neither of the index's whole-site paths runs in the checks above. `npm run check:usage-index` boots its own dev site with WP-Cron off, adds 60 pages bound to the phone, and records what the index holds after those saves. Then it deletes the index and checks that each path puts every row back, and nothing else:

- `wp voyager-open-blocks reindex`, run through WP-CLI, over more than one batch of 50 posts;
- the backfill that activation starts: the plugin is deactivated, a page is added while it is off, the plugin is activated again, and the backfill event runs as WP-Cron would. The plugin version is unchanged, so the check on `init` starts nothing, and activation is the only way in.

It also checks the "Shown on" line's order: titles in the database's order, so "Usage check 10" before "Usage check 2". `--plant activation` takes the backfill off the activation hook and `--plant reindex` replaces the command with one that reports success and indexes nothing; each run then passes only when the check fails that path and passes the rest. CI runs all three ([`e2e.yml`](../.github/workflows/e2e.yml)). `--plant crash` makes the harness throw before it boots the site, and `npm run check` runs it, through the check's known-answer test. It exits 0 on a pass, 1 when a path fails, and 2 when it could not tell. A crash is a run that could not tell: 2, even after every path it reached passed, and 1 only when a path had already failed.

### Site checks

Each of these runs against the local site and exits non-zero on the first mismatch.

- **`npm run check:site-data -- --site ../voyager-open-blocks-site`** writes the untidy options in `tests/fixtures/site-data-keys.json` to the site, runs `values()` through `wp eval-file`, compares all 27 `voyager/site-data` keys to the fixture's `expected` values and prints `ok: 27 site-data keys match the fixture`. It puts the previous option values back, pass or fail. `{{year}}` in `expected` stands for the current UTC year. The `voyager_site_*` options are written with their sanitize filters removed, so the check pins `values()` and not the settings page.
- **`npm run check:resolution`** (`node scripts/binding-resolution-check.mjs --site <dir>`) binds one paragraph to `phone` and one to a key the source does not have, then checks that `get-post-blocks` reports the first as `resolved` with a value preview and the second as `fell_back` with reason `unknown_key`. It deletes the page and restores the option, pass or fail.
- **`npm run check:bindable-meta`** (`node scripts/bindable-meta-check.mjs --site <dir>`) checks a stored Bindable post meta row: `get-catalog` lists it, `resolve()` reads it, a `_private` key is refused, and removing the row removes the field.
- **`node scripts/foreign-owner-check.mjs --site <dir>`** checks the voyager-blocks case below, with `tests/fixtures/foreign-site-data.php` standing in for the owner.

## Cache check

`npm run cache-check` asks whether a Site Data change reaches a page that a cache has already stored. It boots Playground with one cache, publishes a page whose paragraph is bound to `phone`, changes the phone over REST, and looks for the new number. It exits 0 when the change reached the page (fresh), 1 when it did not (stale), and 2 when it could not tell. It runs in CI, one check per cache and mode ([`cache.yml`](../.github/workflows/cache.yml)). Each row passes on the outcome in the harness's result file, not on the exit code alone: Node also exits 1 when it crashes. Its logic has a known-answer test that `npm run check` runs.

- **`--real`** is for caches that serve pages from PHP inside Playground: `npm run cache-check -- --plugin wp-super-cache --real`. It loads the page twice as a visitor, checks that the second load came from the cache, changes the phone and loads it again. A footer comment unique to each render tells a cached copy from a fresh one.
- **`--spy`** is for caches in a server or a CDN, and for plugins that cannot be installed here: `npm run cache-check -- --plugin spinupwp --spy`. A test mu-plugin records the cache plugin's own purge hooks and its outgoing HTTP (`pre_http_request`) during the change, and the run passes when one of them names the page, or purges everything. When the pack's adapter for the cache is loaded and judges the cache off, the run is unmeasured, not stale: the setup did not turn the cache on as a host would, so a stale page would prove nothing. `dummy` is a pretend cache with a CDN API, offered to the pack as a cache adapter.
- **`--no-purge`** is the control: it empties the pack's purge through contract 2's filters (`voyager_open_blocks_cache_adapters` and `voyager_open_blocks_purge_urls`), so the page must go stale. **`--stand-in`** adds the harness's own hand-run of contract 2 beside the pack's purge, the positive control for `--spy`.
- **`--pages <n>`** publishes n pages bound to `phone`, one at a time, and measures the last, which must have the highest ID: `npm run cache-check -- --plugin wp-super-cache --real --pages 51`. The purge cleans at most 50 pages one by one, oldest ID first, so the 51st is one only `purge_all` reaches. The default is 1.
- **`--lockdown`** turns on WP Super Cache's Lock Down before the run, as its settings page does (`WPLOCKDOWN` `'1'` in `wp-cache-config.php`): `npm run cache-check -- --plugin wp-super-cache --real --lockdown`. Lock Down keeps the cached pages through a traffic spike, so the page must go stale.

The pack purges when Site Data changes ([contract 2](v2-contracts.md#2-purge), `inc/freshness/purge.php`), so `dummy --spy`, `wp-super-cache --real`, `wp-super-cache --real --pages 51` and the `--spy` rows of SpinupWP, Nginx Helper, LiteSpeed Cache, WP Rocket, Cloudflare and W3 Total Cache expect fresh. `dummy` hears it through its adapter. WP Super Cache hears it two ways. The purge calls `clean_post_cache()` for each page that shows the field, up to 50, and WP Super Cache purges that page on that hook. The pack's WP Super Cache adapter (`inc/cache/wp-super-cache.php`) hears the rest: it deletes each URL on a page purge, and clears the site's cache on `purge_all`, which is what refreshes a page past the first 50. The `--no-purge` rows are controls and stay stale for good. On a one-page row the empty URL list switches the whole purge off. On the 51-page row the purge still cleans the first 50 pages and sets `purge_all`, and with no adapter left nothing reaches the 51st. `wp-super-cache --real --lockdown` expects stale too: in Lock Down WP Super Cache hooks none of its own purges, and the adapter is inactive, so nothing deletes the page. It goes fresh if the adapter purges through Lock Down. The PLUGINS table in `scripts/lib/cache-check.mjs` and the fixtures in `tests/fixtures/cache-check/` hold the details of each cache.

WP Super Cache is pinned at 3.1.5, read from its source. The harness turns it on with its own `wp_cache_enable()` after activation, and leaves it in "simple" mode, where `wp-cache-phase1.php` serves stored pages with `wp_cache_serve_cache_file()`. Its purge entry points are `wpsc_delete_url_cache()` and `wp_cache_clear_cache()` in `wp-cache-phase2.php` and `wpsc_delete_post_cache()` in `inc/cache-files.php`. Playground runs PHP with the SAPI name `cli` and sets `PHP_SELF` to the request path, which makes `wpsc_is_backend()` refuse to cache any page but the front page. A WP Super Cache plugin file in the fixtures sets `PHP_SELF` to `/index.php`, as Apache or nginx would.

Three caches live in the web server and run with `--spy`. None of them hooks `clean_post_cache`, so only the pack's adapter for each (`inc/cache/`) tells it about a change. Each is installed from WordPress.org at a pinned version, read from its source, and its setup fixture checks that the plugin, by its own test, says its cache is on.

- **SpinupWP 1.9.1** (`spinupwp`). Its page cache is on when `SPINUPWP_CACHE_PATH` is a constant or an environment variable (`Cache::is_page_cache_enabled()` in `src/Cache.php`). The harness writes the constant into `wp-config.php`. The adapter calls `spinupwp_purge_url()` and `spinupwp_purge_site()` in `functions.php`, and the harness records `spinupwp_url_purged` and `spinupwp_site_purged`, which SpinupWP fires as it purges, whether or not a cache file was there to delete.
- **Nginx Helper 2.4.1** (`nginx-helper`). It purges nothing until Enable Purge is on. The fixture saves its settings as its settings page does, with Enable Purge on and the "Delete local server cache files" method, and the harness writes `RT_WP_NGINX_HELPER_CACHE_PATH` into `wp-config.php`. The default method sends a GET to the site's host without its port, which here would reach whatever listens on port 80. The adapter calls `purge_url()` and `purge_all()` on the `$nginx_purger` global, and the harness records the filter `rt_nginx_helper_purge_url`, which every purger runs on the URL it was given, and `rt_nginx_helper_after_fastcgi_purge_all`.
- **LiteSpeed Cache 7.9.3** (`litespeed-cache`). Its page cache is on, `LITESPEED_ON`, when the server allows it and its Enable Cache setting is on. A LiteSpeed server allows it by setting the server variable `X-LSCACHE`, and an mu-plugin in the fixtures sets it. Playground's SAPI name `cli` allows it too: LiteSpeed Cache takes it for WP-CLI and defines `LITESPEED_CLI`, which also makes it queue each purge in an option instead of sending its `X-LiteSpeed-Purge` header. The adapter fires `litespeed_purge_url` and `litespeed_purge_all`, and the harness records `litespeed_purged_link` and `litespeed_purged_all`, which LiteSpeed fires once a purge is queued.

Three more run with `--spy`, each in its own way:

- **WP Rocket 3.24** (`wp-rocket`), through a stand-in. WP Rocket is not on WordPress.org, so the harness cannot install it. A stand-in mu-plugin, `tests/fixtures/cache-check/wp-rocket-stand-in.php`, defines `rocket_clean_files()` and `rocket_clean_domain()` with their signatures in WP Rocket 3.24 (`inc/functions/files.php`), and records each call, with its URLs, through an action of its own. It cleans nothing. The adapter calls `rocket_clean_files()` with the page URLs, and `rocket_clean_domain()` on `purge_all`. Real WP Rocket also hooks `clean_post_cache`, which the stand-in does not, so the row measures the adapter alone.
- **Cloudflare 4.14.5** (`cloudflare`). The plugin purges Cloudflare's edge through Cloudflare's API with `wp_remote_request()`, so the harness's `pre_http_request` recorder sees the purge and answers it before it leaves the site. External HTTP is blocked, so nothing reaches Cloudflare. The plugin has no purge by URL, so the adapter calls its `purgeCacheEverything()` (`src/WordPress/Hooks.php`), and the run passes on the request whose JSON body is `{"purge_everything":true}`. The plugin sends it only when its page cache is on, it has a domain, and Cloudflare's API names that domain's zone. `tests/fixtures/cache-check/cloudflare/setup.php` turns the page cache on and stores the site's host as the domain, and an mu-plugin, `cloudflare-api.php`, answers the zone lookup, and the page rule and HTTPS lookups a publish makes, with the fields the plugin reads. Setup checks each through the plugin's own code.
- **W3 Total Cache 2.11.0** (`w3-total-cache`), installed from WordPress.org. Its page cache does not hook `clean_post_cache`, so only the pack's adapter tells it about a change. It keeps its settings in a file, `master.php` in `wp-content/w3tc-config`, not in an option. `tests/fixtures/cache-check/w3-total-cache/setup.php` turns Page Cache on as its General Settings screen saves it, with `Config::set()` and `Config::save()`, and reads it back through `w3tc_config()`. It checks that the message bus is off, so the plugin flushes locally (`CacheFlush.php`), and that permalinks are pretty, without which the screen turns Page Cache back off. It writes no `advanced-cache.php` and no `WP_CACHE`, so no cached page is served and every load is rendered. The adapter calls `w3tc_flush_url()` once per URL and `w3tc_flush_posts()` on `purge_all` (`w3-total-cache-api.php`), and the harness records the actions `w3tc_flush_url`, with the URL, and `w3tc_flush_posts`, which `CacheFlush_Locally` fires as it flushes and the page cache listens to.

## Sites running voyager-blocks

The two binding sources keep the names they have in the voyager-blocks plugin, so content written for either resolves on both. When voyager-blocks is active it registers them first (at `init` priority 5), and this plugin stands aside: it registers neither source, the options nor Settings > Site Data. `get-catalog` and `bind` then use the owning plugin's fields, read from its `voyager_binding_sources` definition. When the owner does not describe its fields, `fields` is `null` and `bind` refuses the source.

## Releases

release-please opens the release pull request and writes `CHANGELOG.md`. You don't tag by hand. On the release pull request, `npm run changelog:fold` writes the notes in `unreleased/` into `readme.txt`'s changelog and deletes them. The steps are in [CONTRIBUTING.md](../CONTRIBUTING.md#how-a-release-happens).

`npm run zip` writes `voyager-open-blocks.zip` from the `files` list in `package.json`. Pushing a `v*` tag runs [`release.yml`](../.github/workflows/release.yml): it builds, zips, checks the zip and attaches it to the tag's GitHub release, creating the release if it does not exist. A tag with a suffix (`v0.2.0-rc.1`) makes a pre-release. The tag's version, without the suffix, must match `Version` in `voyager-open-blocks.php`, and a version bump moves `Stable tag` in `readme.txt` with it.

`readme.txt` is the WordPress.org listing. The zip ships it, and Plugin Check must report no errors on the plugin installed from the zip: `npm run plugin-check` runs it, and CI runs it on every pull request. Run against this checkout linked into a site, Plugin Check also reports files the zip leaves out (`.git`, dotfiles, `playground/`).
